# Server records

Incident evidence and measurements behind the rules in
[`.claude/rules/server.md`](../rules/server.md). Each section states when it was
measured and on which version; re-measure before treating a number as current.

## Project-cache watcher stall

Measured 2026-09-08, `server/projects-cache.ts`, registry with 19 projects.

**Project-cache watchers must prune content before traversal** (`server/projects-cache.ts`, 2026-09-08): `depth: 2` still visits each session's content, captures, and dependency directories. Every session server primes all registered projects, so unrelated workspaces can stall a newly opened session's first HTTP response. On a registry with 19 projects, `/api/launch` returned in 354 ms but the document waited 37.7 s; running only `primeProjectCache` (no backend or downloads) stalled the event loop for 32.8 s. Use `depth: 1`, disable symlink following, and an `ignored` predicate that admits only session directories and their direct `session.json` / `history.json` / `thumbnail.png` files. Filtering emitted events is too late. The same probe then completed in 0.76 s and the full document wait fell to 0.74 s. Keep real watcher tests for content isolation AND atomic metadata replacement, history/thumbnail writes, and session creation/removal.

2026-09-24: the cache now keeps one layer watcher per project on `<root>/.pneuma` (see [Watcher backend](#watcher-backend)); its ignore predicate admits `project.json`, `cover.png`, the session directories and their three metadata files, so manifest and cover changes refresh the entry too. On macOS the native backend receives every session-content event of that project and drops it in JS; chokidar still prunes on Linux/Windows. Priming the owner's 20-project registry in a real `--viewing` session: 19 roots registered within 8 ms, every scan done 40 ms after the server listened (the chokidar-era prime took 0.86 s).

## Bun file-watcher deadlock

Measured 2026-09-02 on macOS arm64.

**Bun <= 1.3.13 在 macOS arm64 上会把整个 server 死锁(2026-09-02 实测)**:症状是「seek 几下视频整个应用卡死,刷新都没反应」——其实和视频无关。`sample <pid>` 看到主线程和 `File Watcher` 线程都停在 `_os_unfair_lock_lock_slow`、0% CPU、所有路由与 WS 全死、Vite 还活着(所以 HTML 能刷出来但 API 全挂)。根因是 Bun 运行时的锁序倒置(分配器锁 vs 线程池锁,oven-sh/bun#26762,mimalloc v3 升级修的),触发条件是 chokidar 监听的工作区里高频 mkdir/rename/rmdir——plotwise 播放时后台预生成分支正是这种负载(`nodes/<id>/` 落盘、`course.json.lock` 反复出现消失)。复现:用生产 `startFileWatcher` + 某个 mode 的 `viewer` 配置起一个 Bun 进程,另一进程循环「建目录写文件 → 改名 → 加锁目录 → 删旧目录」,1.3.11 在 540/1000 轮、1.3.12 在 190 轮、1.3.13 在 70 轮挂;1.3.14 与 1.4.0 跑满 3000 轮。所以 `engines.bun`、`bin/pneuma.ts::checkBunVersion`、CI `setup-bun`、`desktop/scripts/download-bun.mjs` 四处都抬到了 >= 1.3.14(CI 与桌面钉 1.4.0)。**四处必须一起动**——桌面端自带 Bun,用户升级本机 Bun 救不了桌面 app。别在应用层「绕」这个 bug(加轮询、去锁目录只是把触发概率调低)。

## Range responses and Blob slices

Measured 2026-09-02 on Bun 1.4.0.

**Bun 1.4.0:切片后的 `Bun.file().slice(a,b).stream()` 吐出整个文件,`/content/*` 的 Range 响应因此全量返回(2026-09-02 实测)**:`new Response(file.slice(a,b))` 本身是对的(Blob 体、长度对),但 Hono 的 `cors()` 等任何中间件为了盖 header 都会 `new Response(res.body, …)` 重包一次——`res.body` 走的就是那条坏掉的 stream 路径。结果是 `Content-Range: bytes 0-1023/7086087` 配上 7 MB 的 body,Chrome 直接判媒体不合法(`MediaError.code === 4`,`networkState 3`):plotwise 舞台全黑、任何 mode 的视频 seek 都失败;而已经被浏览器整份缓存过的 clip(304)照常能放,所以看起来"有的能播有的不能"。现在 Range 分支用 `Readable.toWeb(createReadStream(absPath, { start, end }))`,不依赖 blob 切片在重包后还成立;stream 体 Bun 会按 chunked 发并丢掉显式 `Content-Length`,总长靠 `Content-Range` 给。`server/__tests__/content-route.test.ts` 现在**和生产一样先挂 `cors()` 再挂路由**,并断言 partial body 的字节数——之前那份只查 header 的测试在坏版本上照样全绿。教训:凡是返回 Blob 体的路由,测试要读 body,而且要在和生产相同的中间件链下读。

## Virtualenv kills the file watcher

Measured 2026-09-02 during a plotwise session.

**文件监听会被一个工作区内的 virtualenv 无声弄死,而且服务重启时还会在 Bun 的分配器锁上卡几分钟**(2026-09-02 plotwise 实测):接地子代理在 `bayes/evidence/` 下建了 `.venv`(12,704 个文件),`DEFAULT_IGNORE` 有 `node_modules` 却没有 `.venv`/`__pycache__`。之后 course.json 每次变化服务端都看得到(`/api/files` 是现读磁盘的,**它证明不了监听还活着**),浏览器却一条 `content_update` 都收不到——用户看到的是"续段明明拍好了,页面一直转圈"。判别方法:往被监听的目录里写一个 `.md` 探测文件,同时用一个被动 WebSocket 客户端连 `/ws/browser/<sid>` 看 12 秒内有没有 `content_update`;没有就是监听死了,只能重启。重启前先把 venv 挪走:带着 17k 文件起服务,主线程会在 `_os_unfair_lock_lock_slow` 里转好几分钟(`sample` 看主线程 760/812 个样本在锁上,CPU 却有 13%——不是死锁,是 lstat 风暴下的锁争用),`/api/session` 超时,页面停在 "Loading…"。修法两层:监听忽略表对齐 `shadow-git.ts::BASE_EXCLUDE_RULES`(`.venv`/`venv`/`__pycache__`/`site-packages`/`*.pyc`/各种 cache),以及 mode 的 brief/SKILL 明说"环境建在工作区外"。**两张排除表以后要一起改。**

2026-09-24:判别方法改成看 `GET /api/session` 的 `watcher.lastEventAt`(写探测文件后它必须前移)。native 后端不能剪枝,被忽略子树里的洪水照样进 JS 再丢:`watch-contract.test.ts` 的 5,000 次写入(子进程写)让监听进程花 20-22 ms CPU(chokidar 13-14 ms),之后的写入照常到达。

## Binary files in the snapshot

Measured 2026-09-23 on a sprite workspace (1.6 GB, 2,818 files matched by `**/project.json`, `**/refs/**/*`, `**/motions/**/*`).

`GET /api/files` read every match with `readFileSync(path, "utf-8")`: 2,727 frame PNGs, 20 WebM, 20 MP4 and 10 animated WebP became 745 M characters of U+FFFD-inflated text (a 400 KB PNG decodes to about 1.2 MB). The response was 1.89 GB; first byte after 63 s, complete after 81 s, the server's RSS 122 MB -> 6.7 GB. In headless Chrome the fetch reached 1.26 GB in 14.5 s, the renderer rose to 1.8 GB with a 2.6 s long task, and the request ended `net::ERR_ABORTED`. `App.tsx` never called `markFilesHydrated`, so the viewer showed "No character yet" for as long as it stayed open (183 s run). `src/ws.ts` repeats the same fetch on every reconnect. The owner's installed Desktop 3.52.1 ships the same route.

After `readWorkspaceText` (binary -> `{ path, content: "" }`), the same workspace's snapshot is 2.8 MB (41 JSON bodies, 2,777 path-only entries), 0.12-0.4 s warm. The watcher flush applies the same rule; before it, a watched `**/*.woff2` (webcraft, kami) reached every browser as mangled text. `readWorkspaceText` is deliberately not `isBinarySeedFile`: the seed question ("must this be copied byte-for-byte?") may answer yes for text such as SVG, while a wrong "binary" here hides text a viewer reads. Tests: `server/__tests__/binary-snapshot.test.ts`.

## Watcher registration cost

Measured 2026-09-23, macOS arm64, Bun 1.4.0.

chokidar 5 has no FSEvents backend; its Node handler opens one `fs.watch` per file and per directory. Bun's per-file registration is superlinear and synchronous on the main thread. Opening N watches in one process: 250 -> 43 ms, 1,000 -> 1.4 s, 2,000 -> 2.5 s, 3,000 -> 11.1 s, 4,000 -> 69.2 s. A `--cpu-prof` of a sprite viewing session (2,882 watched files, `HOME` pointed at an empty directory so no projects-cache work ran) spent 73.4 s of 76 s in native `watch`. `/api/session` stalled up to 24 s, and the page's own `GET /` waited about 33 s, so the first render came at 40.8 s even after the snapshot fix. With sprite's frame, cell and scratch directories in `ignorePatterns` (198 watched files), the server is ready in 0.9 s and the first render lands 4.6 s after navigation. A single recursive `fs.watch(root, { recursive: true })` set up in 21.8 ms on the same tree. It would remove the per-file cost for every mode, but it has no pre-traversal `ignored` predicate: on Linux, where recursion is emulated per directory, an ignored `node_modules` or `.venv` would presumably still be walked (not measured). The awaitWriteFinish, symlink and deletion semantics would also need re-verifying, so it has not replaced chokidar.

2026-09-24: chokidar is no longer the macOS default. The native backend registers the root once (3-4 ms at any size) and then indexes the watched files with one pruned walk: `[watcher] native ready in 72-79ms` on a 534-directory / 14,327-file backlot tree, where chokidar under Bun took 21.4 s and blocked the event loop for all of it (the browser WebSocket could not connect until 21.4 s after the server listened). The per-file cost still applies to `PNEUMA_WATCHER=chokidar` on macOS. See [Watcher backend](#watcher-backend).

## Watcher backend

Measured 2026-09-24 on macOS arm64 (Darwin 27.0.0), Bun 1.4.0, chokidar 5.0.0; Linux in Docker (`oven/bun:1.4.0`); Windows not measured. The design measurements' scripts and raw outputs were kept outside the repository; these are the numbers the rules rely on.

**Root cause of "replacements lost".** Bun keeps one FSEventStream per process for every `fs.watch`, recursive or not, and on each add or close stops it and recreates it with `kFSEventStreamEventIdSinceNow` (`src/runtime/node/fs_events.rs`). Nothing between stop and start is replayed. The gap grows with the paths in the stream (`fs.watch` on a fresh file right before a rename-over of `edl.json`, 10 tries each):

| Paths in stream | No add | Add just before | Close just before | Loss window |
|---|---|---|---|---|
| 10 | 10/10 | 9/10 | 9/10 | coincident only |
| 300 | 10/10 | 9/10 | 10/10 | 5/6 at 0 ms, 6/6 from 5 ms |
| 1,200 | 10/10 | 0/10 | 0/10 | 0/6 at 0-5 ms, 3/6 at 10-20 ms, 6/6 from 40 ms |

chokidar adds a watch for every path that appears and closes one for every path that disappears, so each `writeJsonAtomic` (temp file, rename, temp gone), every `.work/` scratch directory and every rendered clip opened a hole in a large tree. The incident: backlot's `cut --finish` rewrote `cut/edl.json` on the owner's 391-directory project and the open Cut stage kept the old film; plain chokidar reported 1 of 3 replacements under Bun (3 of 3 under Node), and 2 of 3 on a synthetic 400-directory tree. A recursive native watch added beside chokidar was deafened by the same churn: 0 of 3 replacements issued during chokidar's 8 s registration on the 534-directory clone, 3 of 3 after it. Coexistence was never the problem (a steady set of per-path watches, or the project cache's 274 chokidar handles, deafened nothing); churn is. An in-place write opens no hole, which is why `touch edl.json` unstuck the viewer.

**Backends.** Recursive native `fs.watch` on macOS: setup 3-4 ms at any tree size (chokidar: 822 ms for 300 files, 17.7 s for 1,200), median latency 11 ms, 3/3 rename-overs everywhere, 5,000- and 20,000-write floods delivered with 3/3 afterwards, symlinks not followed; every event is typed `rename` and drops are never surfaced, so the layer stats each notice. On Linux Bun walks the tree without pruning (2,105 inotify watches where chokidar with the function `ignored` holds 209, ready in 9 ms) and reports `error` when the watch limit is hit, so chokidar stays the Linux default and native falls back to it on ENOSPC/EMFILE. Windows: chokidar by inference (per-directory 4 KB buffers; a recursive native watch would funnel the whole tree through one, overflowing into the layer's rescan). `@parcel/watcher` 2.5.1 was measured and rejected: it reported "Events were dropped by the FSEvents client" on the 5,000-write flood Bun's own stream absorbed, then delivered 2 of 3. chokidar with `usePolling` delivers but costs 12.5% of a core idle at 100 ms.

**The implementation, measured.** The real `--viewing` backlot session on an APFS clone of the 534-directory / 14,327-file tree, a passive `/ws/browser/<sid>` client, rename-overs of `tanka-launch-v4/cut/edl.json` from a separate process: `native ready in 72-79ms`; one rename-over at 47, 479 or 931 ms after the server listened (while the project cache primed 19 roots) arrived with its own content in 524-531 ms, 3 of 3; later ones 9 of 9 at 519-532 ms (200 ms stability + 300 ms debounce, kept on purpose). Two writes closer than ~350 ms surface as the newer content only: the flush reads the file when the debounce fires, as it did with chokidar. `PNEUMA_WATCHER=chokidar` on the same tree: ready in 21.4 s with the event loop blocked throughout, then 4 of 4.

**A fresh watch can come up deaf under churn.** In the contract suite, after rapid add/close churn in a process that also held other watchers (a test file had left the project cache's native watchers on the owner's 19 projects running), a newly registered recursive watch occasionally got zero callbacks for its whole 3 s case, while a fresh raw `fs.watch` on the same root, created at that moment, heard the write, and a long-lived canary watch heard its own. It needed churn plus that leftover state; raw probes (19 held roots, close then register, bursts of 21 registrations, root removal) never reproduced it in 400+ attempts, and the production sequences (workspace watcher, then 20-root priming, a runtime project registration, an eviction) stayed live 50 of 50. So the rule is: register each root once, never churn; test files that start a server must call its `cleanup()`, and the contract suite proves each registration live before a case and re-registers (logged) if Bun delivered nothing. Worth adding to the upstream Bun issue about the stream rebuild.

**Review amendments (2026-09-24).** Four gaps from the read-only review, each now a case in `watch-contract.test.ts`. (1) A case-only rename on case-insensitive APFS (`page.md` → `Page.md`) left the old spelling live: `lstat("page.md")` succeeds, so neither the notice nor a rescan deleted it. The layer checks the on-disk spelling with `realpathSync.native` (for a symlink, `realpath` of the parent plus an exact `readdir`, since `realpath` follows the link), compared after NFC normalization. (2) An ENOSPC fallback during the initial walk resolved `ready` before chokidar listened; chokidar's `ignoreInitial` then hid files created during the switch in a directory the walk had already listed. `boot()` now waits for the replacement and reconciles before `ready`. (3) An overflow rescan tested only existence, so a file replaced by a directory kept its stale entry. (4) `lstat` errors in the walk were swallowed: a directory with mode 0444 (listable, children not stat-able: EACCES) gave an empty index and `degraded: false`.

**Real-session findings, round 2 (2026-09-24).** A verifier drove real sessions with headless Chrome (evidence kept outside the repository). (1) `PNEUMA_WATCHER=chokidar` on the sprite tree: chokidar's ready took 2.3-2.6 s, and an edit 610 ms after the session's ready line never arrived (no frame, `lastEventAt` null). chokidar's `ignoreInitial` hides what changes while it registers, and the index was then built from the changed tree. The index is now taken synchronously at creation and reconciled after ready. (2) Native: in 29 launches, 6 edits made 10-17 ms after the workspace watcher was created were lost; the same slice with an empty HOME delivered 14 of 14. That window was projects-cache priming one native watch per registered project, each rebuilding the shared stream. `bin` now primes first, and every layer registration or close makes the other live watchers reconcile. (3) 300 scratch `.json` files written and renamed away within ~50 ms produced 300 delete frames and filled the 600-event replay buffer; none had been reported or listed. The file-watcher now sends a delete for a path the layer knew (`deleted.known`: indexed at creation or reported since) or a browser may hold (a snapshot listed it or an update carried it). A first version used only the second condition, and in doc mode deleting an unchanged `img/pic.png` that `README.md` displays sent nothing: the viewer kept showing the deleted picture (main sent the delete in 113 ms). Dropping only a vanish still pending stability would have kept these: each file was already gone when its first notice was classified. (4) A `python -m http.server` on 127.0.0.1:18791 did not stop `Bun.serve` binding the wildcard 18791, and `localhost:18791` reached the other process; the bind helper now skips a port that answers a loopback connect.

**Windows: a folder with subfolders cannot be moved or renamed while chokidar watches it.** chokidar (the Windows default) holds a handle on every watched directory, and Windows refuses to rename a directory while handles are open beneath it: the contract suite's move-out got EPERM on windows-latest (2026-09-24), and moving such a folder out of the workspace in Explorer while Pneuma runs fails the same way. It is the same on main; `PNEUMA_WATCHER=native` (one handle, on the root) avoids it.

**Shutdown.** Closing chokidar's per-path watches costs one stream rebuild each, synchronously: awaiting the workspace watcher's close at shutdown blocked a chokidar-backed session on the 14k-file tree past its 4 s force-exit fuse. `bin/pneuma.ts` therefore leaves the watcher to process exit. The project-cache watchers too (`cleanup({ exiting: true })`, 2026-09-24): with `PNEUMA_WATCHER=chokidar` closing them took 2.7 s on a real registry (0.8 s for 20 small projects), and the agent is killed only after cleanup returns, under the same fuse. Shutdown now takes 3-5 ms on either backend.
