# Backend Rules (claude-code / codex / kimi-cli)

## Baseline

- **`backends/index.ts` is a pure registry** over per-backend manifests. No `if (type === ...)` conditionals outside this file — backend knowledge lives behind `BackendModule`.
- **Read the backend's own README first**: `backends/claude-code/README.md`, `backends/codex/README.md`, `backends/kimi-cli/README.md` — protocol details, lifecycle quirks, and version-compat branches live there, not in AGENTS.md.
- **All backends run stdio** (Claude: stream-json NDJSON; Codex: `app-server` JSON-RPC; Kimi: ACP JSON-RPC via `kimi acp`). `/ws/cli/:sessionId` is legacy-only.
- **Lifecycle tests reuse the shared harness**: `backends/__tests__/lifecycle-harness.ts` runs the same 6 scenarios against every backend. New backend behavior belongs in the harness when it's cross-backend, in the backend's own `__tests__/` when not.
- **Install conventions** are data on the manifest (`skillsDir` + `instructionsFile` on `BackendModule`): Claude `.claude/skills/` + `CLAUDE.md`; Codex `.agents/skills/` + `AGENTS.md`; Kimi `.kimi-code/skills/` + `AGENTS.md`. Server code gets them via `getInstallConventions(backendType)` — never hardcode paths.

## Gotchas

- **Codex 的 `/compact` 与 `error` 通知都不能按 Claude 的直觉处理**:app-server 不解析 slash command,把 `/compact` 当文本发进 `turn/start` 就是给模型两个单词的 prompt——adapter 必须拦截裸 `/compact` 走 `thread/compact/start`(`codex-adapter.ts::startCompaction`),并把 `compact` 塞进 `slash_commands` 让菜单可见。v2 的 `error` 通知把文本嵌在 `params.error.message`(还有 `willRetry`),只读顶层 `params.message` 会让每条现代错误都显示成 "Unknown error"——统一走 `describeErrorNotification`,别再手写第四种读法。压缩完成的协议回显是一条 `system_event { subtype: "compact_boundary" }`,与 Claude 的 `system.compact_boundary` 同一形状,前端只认这一种。
- **Claude 的模型开关必须走 `control_request`,顶层帧会被静默吞掉**:stream-json 的输入读取器**接受** `{"type":"set_model","model":"haiku"}` 这一行、不报错、也不回任何 response——然后**丢弃**它,下一轮照旧跑在原模型上。生效的唯一形状是 `{"type":"control_request","request_id":…,"request":{"subtype":"set_model","model":…}}`(CC 2.1.220 实测:顶层帧 → `modelUsage: claude-opus-5`;control 帧 → `modelUsage: claude-haiku-4-5-20251001`)。这条 bug 隐形了很久,因为 bridge 做了乐观 UI 更新——picker 换了标签、`session.state.model` 也变了,只有真实计费模型没变。`set_permission_mode` / `interrupt` / `stop_task` / `end_session` 同属那个 subtype 白名单,新增任何一条都用 `sendControlRequest`,别自造顶层帧。
- **Claude 的一条 assistant message 是按 content block 逐帧发的,持久化必须 merge 而不是 replace**:`tool_use` 一帧、`text` 一帧,`message.id` 相同。bridge 早先直接覆盖同 id 的 history 条目,于是**每条多块消息只剩最后一块**——四份线上 history(34 / 732 / 415 / 208 条 assistant)里没有任何一条带两个 block,而那条 `Task` 的 tool_use(= 它 spawn 出来的子代理的锚点)刷新后就消失了,子代理的回复却还在,看起来像「凭空冒出来的一段话」。现在 `handleAssistantMessage` 按 JSON 全等去重后拼接(已有的在前),**每一帧只广播它自己**——浏览器也按 `message.id` 合并,晚到/重连的浏览器走 `message_history` 与 replay ring,广播合并结果等于第 k 帧重发前 k-1 块,按消息长度是 O(N²) 字节。这条规则本身住在 `core/utils/content-blocks.ts`,前后端同一份实现(`src/store/helpers.ts::mergeContentBlocks` 只是包了一层「两边都空就返回 undefined」),别再抄第二份。顺带一提:子代理的归属键只有 `parent_tool_use_id`(= spawn 那次调用的 `tool_use.id`),`PermissionRequest.agent_id` 是 CLI 给的显示名、不是身份,别拿它当 id 用——`control_request.can_use_tool` **只**带这个名字,所以 Claude 的权限横幅认不出是哪个子代理在问(Pneuma 自己合成的 AskUserQuestion 权限例外,它从 assistant 帧来,带得上 `parent_tool_use_id`)。
- **`--resume` 的去重必须按「哪个代理」分桶,否则子代理会吃掉别人的消息**:`handleAssistantMessage` 里那条「同文本 + 新 `message.id` + 之后没有真实用户输入 ⇒ 覆盖上一条 assistant」的 resume 去重,原本用 `findLastIndex(h => h.type === "assistant")` 找「上一条」,**不看 `parent_tool_use_id`**。于是两个子代理都回 "PASS" 时后一个把前一个覆盖掉;子代理复述了一句 root 说过的话时,**被覆盖的是 root 那条**——连带 spawn 的 `tool_use` 锚点(子代理卡片就是挂在它上面的)一起消失。现在:带 `parent_tool_use_id` 的帧**完全不走**这条路(CLI resume 重放的是 root 的 transcript,不是某个已结束代理的私有轮次),root 帧只在 root 归属的条目里找候选。另外两点同属这条路:覆盖时要把旧条目的**非 text 块**带过去(re-emit 只有文本,整条替换会把刚 merge 好的 tool_use 又抹掉),而 re-emit 同样是**按块逐帧**来的,所以「只有 tool_use、且这些块已经在库里」的那一帧对 history 是 no-op、只广播。`server/__tests__/ws-bridge-subagents.test.ts` 钉住这四种形状。
- **模型列表只在 `initialize` control response 里,`system.init` 没有**:`system.init` 只报当前那一个 `model`,不带候选列表(实测 key 列表里既无 `models` 也无 `availableModels`)。可选列表来自 `control_request {subtype:"initialize"}` 的成功响应 `response.models[]`——即 Agent SDK `query.supportedModels()` 读的那个东西,每项形如 `{value, resolvedModel, displayName, supportsEffort, supportedEffortLevels, supportsAdaptiveThinking, supportsFastMode, supportsAutoMode}`。`value` 常是别名(`opus` / `default` / `opus[1m]`),`resolvedModel` 才是具体模型,二者可多对一(`default` 与 `opus[1m]` 都解析到 `claude-opus-5[1m]`),所以高亮"当前项"必须选**单一**赢家、不能对每行跑谓词。`WsBridge.requestSupportedModels` 在 `attachCLITransport` 里 fire-and-forget 发这个请求;它与正常 turn 并存无副作用(hooks 照常触发、`system.init` 正常)。老 CLI 答不出 `models` 时回落到 `BackendModule.defaultModels`——**那个静态列表一律写别名,不写钉死的 model id**,钉死的每次发新模型就烂一次(它曾在 Opus 5 与 Fable 都上线后还挂着 Opus 4.7 / Sonnet 4.6)。

- **Codex skill-roots alias expansion misfires**:Codex(0.137)把 skill 列表呈现成 alias 压缩的 roots 表,路径展开由模型自己做,roots 一多就展开错。因此 `generatePneumaSection` 在 `pneuma:start` 块里写死 cwd 相对 skill 路径(mode skill 指针 + `skillPathRule`)。重构指令拼装时**不要删这两行**。
- **Agent-command marker placement**:`<!-- pneuma:agent-command version="..." backend="..." -->` marker 放在 YAML frontmatter **下方**,不是 line 1——Claude Code 与 Codex 都要求 frontmatter 从 line 1 起。Installer 全文扫 marker,不只 line 1。无 marker 的文件视为用户手写,`--force` 之前不覆盖。
- **Codex 不用 custom prompt**:`~/.codex/prompts/*.md` 已被 OpenAI 弃用且有发现回归;handoff-pneuma 走 `.agents/skills`。install 时若旧 prompt 文件还在且带我们的 marker 会顺手删掉(`descriptor.legacyFile`)——只删我们自己写的。
- **指令文件不分叉**:Codex 与 Kimi 各读 `AGENTS.md`,Claude 读 `CLAUDE.md`(repo 根的 CLAUDE.md 只含 `@AGENTS.md` import)。运行时对所有 backend 是同一份语义。
- **Kimi = Kimi Code,不是旧 kimi-cli**:`kimi` 二进制被 Moonshot 整体换成了 Kimi Code(版本号从 1.41.0 **倒退**到 0.26.0——semver 比较是反的,判定新旧只能 probe `acp` 子命令)。skill 发现目录是 `.kimi-code/skills/`(旧 `.kimi/skills/` 新 binary **不读**);`--print`/`--input-format`/`--work-dir`/`-r` 全部消失。协议细节(tool-call 参数流式 partial-JSON 陷阱、`title` 只在 `tool_call` 起始帧是真工具名、`session/resume` 不回放历史而 `session/load` 会、permission round-trip 不答会死锁)见 `backends/kimi-cli/README.md`。
- **Kimi 的 `usage_update` 是"上下文占用",不是 token I/O 拆分,而且晚于 turn 结束到达**(0.38.0 实测):payload 只有 `{used, size}`——`used` 是这个 session 当前占了多大上下文(k3 的 `size` 是 1048576,**空 session 一开就 ~36k**,因为系统提示词本身那么大),**没有** input/output/cache 任何拆分,ACP 里根本不存在这些字段。所以它的正确归宿是 `context_used_percent`(ChatPanel 的 "ctx N%"),`input_tokens` 只能填这个累计值并在 README 里说清它是什么,其余三个字段留 0——**编一个数比留 0 更糟**。另一半陷阱是**时序**:这一帧在该 turn 的 `session/prompt` response **之后**、另一个 stdout chunk 里到(实测同一毫秒,但 promise 已 resolve、微任务已跑完),于是 result envelope 天然滞后一轮:第 1 轮报 0,第 N 轮报第 N-1 轮的快照。想"修"它就得推迟 turn 结束——**别做**,拿实时 idle 换一个装饰性数字不划算。同理:`current_mode_update` 才是 mode 的唯一来源,`config_option_update` 里那份 `mode` 是第二来源,**一个事实两个来源迟早打架**,不要读。
- **ACP `session/prompt` 不能设 RPC 超时**:它到 turn 结束才 resolve,中途还会阻塞在人类批准 permission 上;超时会在长 turn 中途误报。liveness 由 transport-close(进程死亡 reject 所有 pending call)兜底,`AcpTransport.call(..., null)` 即无超时路径。
- **Codex 的 `thread/tokenUsage/updated` 有两个 token 数,拿错那个会渲染出 "ctx 5851%"**:payload 是 `{ total, last, modelContextWindow }`——`total` 是**整个 session 的累计**(每一轮把整份 prompt 重新计一次,长会话轻松上千万),`last` 才是**最近一次请求**、也就是此刻真正占着上下文窗口的量。适配器最初拿 `total` 除窗口,于是 UI 上出现了 5851%。实测一份 194 轮的 rollout:`total.total_tokens` 23,319,931 / 窗口 258,400 = **9024%**,而 `last.total_tokens` 127,291 = **49%**。累计计数器读 `total`,窗口仪表读 `last`,并且**百分比一律 clamp 到 [0,100]**——clamp 不是修复、是兜底,防下一次 payload 改形状又渲染出不可能的数字。这条 bug 能活下来是因为**测试只覆盖了 legacy 扁平 payload**(`params.inputTokens`),v0.114+ 的嵌套分支一条测试都没有;新增协议分支时对着**新旧两条路径**各写一条。
- **Codex 的每条通知都带 `threadId`,不读它子线程就会冒充主线程**(issue #152,codex-cli 0.154.0-alpha.3 盲测实测):`--enable multi_agent` spawn 出来的 agent 跑在**自己的 thread**、同一条 transport 上,`item/*` / `turn/*` / `item/agentMessage/delta` / reasoning delta / `thread/tokenUsage/updated` / `thread/status/changed` / 每个 approval 都带 `threadId`(legacy 的 `execCommandApproval` / `applyPatchApproval` 把同一个值叫 `conversationId`)。`handleNotification` 原本一眼不看,于是子 agent 的文字成了主 agent 的话、**每条子线程 `turn/completed` 都合成一个 `result`**(`num_turns++`、`status_change: idle`、顺手把主线程的 streaming buffer 冲掉)、子线程 `turn/started` 覆盖 `currentTurnId` 让 `turn/interrupt` 打错 turn、子线程的 token usage 把主上下文仪表冲掉,`collabAgentToolCall` 与 `subAgentActivity` 则整块落进 `default:` 消失。四条硬规则:(a) streaming / reasoning / `currentTurnId` / `emittedToolUseIds` / `commandStartTimes` 全部进 per-thread 的 `ThreadState`,**一个扁平字段都不许留**——留一个就够子线程再冒充一次;(b) **子线程的 `turn/completed` 永远不合成 `result`**,不动 root 的 status / buffer / gauge / `num_turns`,子线程的 `error` 只更新它自己的 roster、不发 root `error`——**这条不止管 `turn/completed` 和 `error`**:`thread/compacted`、`model/rerouted`、`codex/event/error|stream_error` 每漏一个 gate 就各漏一次(compaction 的 echo 是一次性的,被子线程花掉,root 自己那条就彻底哑了、还会顶着用户 `/compact` 的 `manual` 标签;reroute 写进 `activeModel` 之后每条 root 消息都被打上子 agent 的模型);(c) 一个 agent 的 anchor(它每条 envelope 的 `parent_tool_use_id`)**第一次见到那个 thread 时就定下、永不改写**——那一刻它已经上了线,迟到的 spawn item 只能沿用 `thread:<threadId>` 这个 fallback 当卡片 id(dedupe 仍按 Codex 的 item id)。**卡片 id 一个 item 只决定一次**并记在 `ThreadState.collabCardIds` 里,否则 `item/started` 发出的 `tool_use` 与 `item/completed` 发出的 `tool_result` 会是两个 id;同理,一个 spawn 同时点名多个 receiver 时谁都不能拿 item id 当 anchor——一张卡片当不了两个会话,多点名的那些各自留 `thread:<id>` fallback;**receiver 还没出现的 spawn 先不发卡片**(等 `item/completed` 点名),提前发就等于给同一个 agent 造了两个身份。(d) **主线程 id 定下来之前,带 `threadId` 的通知要排队**(`preAdoptionNotifications`),不能按 root 处理:RPC response 与后面的通知同在一个 stdout chunk,`processBuffer` 同步派发,而 adopt 还只是一个排着的微任务——resume 回放里的子线程 `turn/completed` 正好落在这个窗口。没有 `threadId` 的通知属于主线程(老 server 没有第二个 thread),这条要有测试钉住。协议事实、四个 anchor 来源、逐通知行为表见 `backends/codex/README.md`(Multi-agent threads)与 `docs/proposals/2026-09-16-subagent-threads.md` §4.1。
- **Codex 报不了成本,别给它开 `costTracking`**:app-server 从不推送 cost(`params.costUsd` 是投机读的,没见过哪个 build 真发)。它确实有估算——`codex/usage/*` **请求**的响应里有 `estimatedUsageCreditsMicros` / `estimatedUsageUsdMicros`(`ThreadUsage`)——但那是 pull 不是 push,没人轮询。开了 `costTracking` 只会在 UI 上钉一个永久的 `$0.0000`。
- **`contextWindow` 能力位现在三个 backend 都是 `true`**:Claude 解析 `/context` 输出,Codex 发 `thread/tokenUsage/updated`,Kimi 发 ACP `usage_update`——三条路都真的报窗口占用。注意能力位声明在**两处**(`manifest.ts` 与 `index.ts` 的实例),改一个不改另一个会被 kimi 的 "manifest 与 backend-instance 同步" 测试抓住;codex 那条没有同类测试,更要手动对齐。
- **`workflowsDir` 装出去的 workflow,注册表在 agent 启动时扫一次,不热更新**(实测 2026-08-12):`Workflow({name})` 确实会解析 `<cwd>/.claude/workflows/*.js`——但**会话中途新写进去的文件,当前 agent 一直看不到**(往本仓库 `.claude/workflows/` 写一个探针脚本后立刻按名调用:`not found`,而同目录下启动时就存在的 `dev-master-orchestrator` 在可用列表里)。今天这不成问题:`installSkill` 在 `bin/pneuma.ts` 的 704/715/2190/2585/2801 全部跑在 `backend.launch()`(748/2620/2823)**之前**,所以新 session 的 agent 一定看得到刚装的脚本。**会咬人的是 in-session 安装**——skill update、seed apply、任何不重启 agent 就重写 `.claude/workflows/` 的路径,写进去的 workflow 当轮不可调用,而且**失败形状是 "not found",看起来像装错了路径,不像缓存**。所以:(a) 脚本自身要同时文档化 `scriptPath` 调法(`${PNEUMA_SESSION_DIR}/.claude/workflows/<name>.js`),那条与注册表无关、随时可用;(b) 新增 workflow 的 skill 版本更新要走 resume(会重启 agent),别指望热生效。
