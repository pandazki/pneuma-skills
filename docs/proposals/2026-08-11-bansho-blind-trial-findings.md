> 自己发现问题。。这样来证明设计已经没有问题了」**
>
> 做法：全新空工作区（`~/bansho-blind`，只有装出去的 skill + `CLAUDE.md`，**零示例板**），
> 任务书**一个字不提**内部概念（`@at`、区域、碰撞、动作名、已知坑一律不给），

## 0. 结论先行：它做成了，而且做得不错

**4 分 48 秒、91 步、四块板复用**，讲「为什么队伍在服务器还没满的时候就崩」。
自己发现并修了三处问题：时长不够（199.7s → 288.3s，用**加实质内容**而不是注水）、
图表吃满整面墙、以及 y 轴单位被裁掉。

**它自己最看重的一句**：「**像素截图改变了产物**——它找到了源码审查和 `check-board`
都漏掉的缺陷。」这正是产品负责人「viewer API 是 agent 的眼睛」那条原则被一个
毫不知情的作者独立验证。

## 1. 最重的一条：**它一个 `@at` 都没用**

统计它写出来的板：`@turn` ×10、`@erase` ×8、`@board` ×1、**`@at` ×0**。

`@at` 是 V2 整包（区域方言 + 碰撞 + `frame-board`）的核心，
**一个冷启动作者读完 skill 之后完全没有伸手去够它**。

不是它不会摆版面——它明确报告了「图表吃满整面墙、没有干净板可用」这个**空间问题**，
然后用 `@erase` + 在擦净的板上继续写来解决。**它遇到了 `@at` 要解决的问题，
却用别的动词绕过去了。**

这不是 bug，是**教学缺口**，而且比缺文档更深一层：文档现在有了
（`board-language.md` 15 处），但 **SKILL.md 里没有任何一个时刻告诉 agent
「此时此刻该考虑摆位置」**。skill 教了节奏（落笔前先看），没教
**「看完之后，除了擦和转，你还可以选地方」**。

**这条不派实现，先记着**——它可能意味着 `@at` 的教学位置错了（在 references 里
是查得到的语法，但作者在**决定怎么摆**的那一刻不会去查语法文档），
也可能意味着它真的不常用。需要第二次盲测来判，不能凭一次就动方言。

## 2. 可直接修的（我已核实根因）

### 2.1 字体 fallback 徽章是**误报**，而且是 skill 的锅

它的报告：「字体栈用的是 skill 推荐的家族，`document.fonts.check` 对所有家族都返回
`true`，但板上每一帧都挂着 `handwriting font fallback` 徽章，无法解释。」

**根因（我查的）：** 它的 `theme.css` 写的是
`"Bradley Hand", "Chalkboard SE", "Segoe Print", cursive` ——**漏了 `HanziPen SC`**。
而 `themes.md` 每一处推荐都带着它（第 51/52/83 行）。检测据此判 fallback。

**两个缺陷叠在一起：**
1. skill 给了**多个不同的字体栈变体**，作者抄了其中一个不完整的；
2. 徽章只说「fallback」，**不说缺哪个家族**——所以作者查了 `document.fonts.check`
   （对系统字体恒返回 true，这是 G8-A 记录过的坑）也查不出来，最后放弃。

**修法：** 徽章必须**点名缺失的家族**；`themes.md` 收敛成一个权威栈。

### 2.2 `check-board` 说「没有任何东西失败」，而 UI 上正挂着警告

它的原话：「`check-board` 反复说什么都没失败，与此同时：图表吃掉了最后一块干净板、
y 轴标签明显被裁、UI 上持续显示 `handwriting font fallback` 徽章。」

**判定：语法有效 vs 视觉有效的分离是对的**（这正是 glance/check/capture 三器官的设计），
**但「Nothing on the board failed」这句措辞太满**——UI 上有已知警告时，
它至少该说「解析层没有失败；板上另有 N 条视觉提示」。

### 2.3 图表容器的名字不能用来擦

它期望 `@erase "waiting-pressure"`（viewer 消息里就这么叫的）能退掉那块板，
得到 `refUnresolved`，随后的 `@turn` 又撞出 `turnOnFullWall`。

**它的评价很准**：「那两条 finding 一旦跑了 `check-board` 就精确有用。
**困惑的地方在于：图表名是合法的 viewer 标识符和摘录，却不是合法的引用目标。**」

### 2.4 定址 capture 不可靠地指向被定址的对象

用图表标注的地址 `capture`，返回的时间戳对、**画面却是更早那块算术板**；
显式 `navigate-to` 之后再 `capture` 仍然是错的面板；
只有拿图表的**轴声明步**的地址才拍到图表本身。

**它留下的未决问题值得单独查**：「我没法判断是**系列/标注动画在正常播放时真的在镜头外**，
还是**只有 capture/navigation 选错了面板**。」——这两种情况严重度完全不同。

## 3. 环境/工具链（不是产品缺陷，但会毁掉每一次冷启动）

- **端口**：任务书让它探 18200–18210，只有 18200 在听，而那是 **viewer API 端口**，
  前端在 **18000**（区间之外）。`.pneuma/config.json` 与 `session.json`
  **都没有记录前端端口**。这条我早就知道（ready 行印错端口），
  但盲测证明了它的真实代价：**一个新用户找不到自己的页面。**
- **17999 更坑**：它服务 Pneuma、接受这个 session id、`navigate_page` 报成功，
  **但显示的是另一个工作区的中文讲稿**。
  **「URL 成功和标签页标题都不是会话绑定正确的证据」**——它只能靠断言 DOM 里的独有文本。
- **共享浏览器状态被别人改掉**：它绑定好的 18000 页面**被另一个会话悄悄换成了 17999**，
  于是 viewer API 失去浏览器连接、一次 `glance-board` **零输出**、
  重试 15 秒超时**零字节**。只有 `list_pages` 能发现标签页被换了。

  ⚠️ **这里有我方责任**：同期跑的碰撞诊断 agent 承认它的 8 个滚轮事件
  打到了这个盲测会话的板上。**观察者污染实验**——已写入长期记忆：
  盲测必须独占端口与浏览器 profile，运行期间不并行派驱动浏览器的任务。

## 4. 它明确称赞的（正面校准）

- **`glance-board` 一旦连上就非常好用**：每块板的占用、笔在哪、擦除历史、
  「还能再写大约 N 步」——**准到足以驱动真实的版面决策**。
- **擦除/转板的保历史模型好用**：最终讲稿复用板面而 Notes 和回拖一点没丢。
- **graph 渲染器几乎零仪式**就画出很清楚的重试环。
- **viewer 给的时长是可测量的**：它当场发现第一版只有 3:20，
  「让修订变得可测量而不是主观」。
