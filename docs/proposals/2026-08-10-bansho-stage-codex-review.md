## P1-1 擦除会连带隐藏**之后才产生**的图层与回指墨迹

`engine/layout.ts:267` 把后文的容器图层 / 回指分配给它们的「家」所在的**已关闭 run**，
而 `viewer/BoardCanvas.tsx:793` 把归属该 run 的每一个 step 都塞进由**先前那次擦除**
控制的 wrapper 里。

**复现：** 画 chart/graph `g` → 擦掉它所在的板 → 后文再给 `g` 追加一个图层。
等价场景：写 `A` → 擦掉 → 后文 `@circle "A"`。新墨迹挂在一个 `clipPath` 已经处于
「全隐」的 wrapper 下，**永远不会出现**。

**为什么这是硬伤：** t=20 的擦除影响了 t=30 才产生的内容，直接违反「擦除只改变此刻板面」，
也戳破了「目标集可在编译期唯一分配」这条**整个「擦除是 Revealable」论证的地基**。
`__tests__/layout.test.ts:180` 明确祝福了这个行为：后来的图层加入了已关闭的 run，
却不在该擦除声明的 targets 里——**声明的目标集与实际被隐藏的 DOM 子树是两个集合。**

这正是我点名要找的那一类：**测试与实现互相同意，两者一起违背契约。**

## P1-2 追加一个 graph 图层，会把**已经写好**的步骤挪到另一块板

parser 把 graph frame 的布局存在文档级可变联合体里（`domain.ts:569`）；追加同名 graph 图层
会**故意重建前缀 frame**（`viewer/reconcile.ts:127`），它的 SVG 尺寸随之改变
（`engine/factories/graph.ts:457`），然后全体重新测量、重新折叠（`BoardCanvas.tsx:739`）。

**复现：** `@board 2`，graph `A → B` 之后跟一段 300px 的段落。后文追加同名 graph 块，
给 A 加四个分支。纯布局从 `282×74` 长到 `282×426`；板高预算 476px 时，
**那段已经写好的段落从第 0 块板跑到了第 1 块板。**

**为什么这是硬伤：** 违反前缀稳定（append 绝不能移动已有 step 的板归属与坐标），
也违反「墨迹是物质」。`layout.test.ts:227` 的前缀性质测试抓不到它——
**它切的是一个已经固定的高度序列，从不演练「追加改变了前缀 step 的派生测量」这件事。**

## P1-3 擦除被归类成「写」，于是镜头在**擦除进行中**就交还了

`BoardCanvas.tsx:988` 把每一个带 revealable 的非镜头步（**包括显式擦除**）都标成
`kind: "write"`；`BoardCanvas.tsx:1079` 在 canonical 舞台 schedule 里重复了一次。
`write` 会清掉 latch（`engine/stage.ts:386`）并成为 `holdUntil`（`stage.ts:473`）。

**复现：**
```markdown
Some explanation
@focus "Some explanation"
@erase
@wait 2
```
已定的规则是「姿态延续到下一个**书写**步才衰减」。实际上寄存器在**擦除开始的那一刻**
就衰减了，宿主可以在橡皮still占着这个窗口的时候把镜头交还给跟随。

**为什么这是硬伤：** 它在擦除窗口开头引入了一次**未被排程的镜头变换**——
G1「五者同轴互斥」当场破：擦和移镜头同时发生。

## P1-4 「from-pose」代理姿态并不是实时跟随真正会停在的位置

`followProxyPose`（`engine/stage.ts:148`）总是把目标放在接近下折线的位置；
而实时跟随有**死区**、目标可见时保持原 y 不动（`viewer/camera.ts:141`），
交还时也保持 y（`camera.ts:268`）。

**复现：** 导演把实时镜头留在 `y=1000`，下一个书写矩形是 `top=1100, bottom=1150`，
视口 600px。实时跟随判定目标可见 ⇒ 不动，镜头停在 1000。
而 canonical 代理算出来是 `1150 − 600 + 96 = 646`。
**下一个镜头动词于是以一次 354px 的跳变开场**，然后才开始平滑插值。

**为什么这是硬伤：** 两个测试各自锁死了**互不相容**的假设——
`camera.test.ts:148` 要求目标可见时保持 y，`stage.test.ts:269` 要求下一次移动
从绝对代理姿态出发。这是本轮第二个「测试互相同意、共同违背契约」的实例，
而且正好落在实现者自己加的那条后补规则上。

## P2-5 装给 agent 的指令**没教镜头语法**，而且**明说不要擦**

`skill/SKILL.md:26` 自称在教方言、`SKILL.md:91` 指向「完整语法」，
但它和 `skill/references/board-language.md` **都只字未提 `@overview` / `@focus`**。

更糟的是 `manifest.ts:88` 仍写着「nothing is erased」，
启动问候 `manifest.ts:240` 直接告诉 agent「**never erase**」。

**为什么这条的产品严重度其实最高：** 整个舞台层是为「让 agent 用得舒服」而做的。
现在 agent 拿不到镜头语法，还被明确劝阻使用一个已经合法的动作——
**能力做出来了，但用它的人被告知不要用。**

## P3-6 `@board 1` 被接受，而已定语法只有 `2|3|4`

`domain.ts:1120` 接受 1–4，`board-language.md:151` 教 `@board 1`，
`layout.test.ts:300` 明确要求它解析成功。

**我的判断（与 Codex 不同）：** 这条是**文档自相矛盾**，不是实现缺陷——
规格标题写 `2|3|4`，可行性稿 §1.1 写的是 1–4，而「单块 = 长条 = 现行线性模式」
是产品负责人亲自锚定的一等公民形态。显式写 `@board 1` 表达「我就是要一块长条」
是合理的作者意图。**修法是把规格标题改成 `1–4`，保留实现**，
而不是把一个能表达清楚意图的写法判成坏步。这条要在修复时明确记下理由。
