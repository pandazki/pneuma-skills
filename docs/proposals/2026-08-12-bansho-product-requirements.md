## 一、起点与内核

### 1.1 最初的诉求（2026-08-06，附三张截图）

> 「我刷到一个这样体验的内容。有点像手写板书的 presentation 模式。。你研究研究有什么
> 相关的基础设施可以用吗？我希望能是**极致的手写动画体验**的效果，又**尽可能灵活可编排**，
> 例如动画能跟其他 svg 或者图表动画进行联合～」

两个词定了这个产品的两极：**极致的手写感** × **灵活可编排**。后面所有决策都在这条轴上。

### 1.2 不做真手写（同日，自我修正）

> 「我觉得全手写有点划不来。。他那个手写也是类似流式播放。。并非真的手写。。
> 我觉得可以有一个抽象。。让支持动画效果的自己实现路径绘制，其他的动画 swipe 也不是不行。」

**这句催生了整个引擎的中心抽象** `Revealable { naturalDuration, kind, seek(p) }`——
手写只是策略之一，降级链 `stroke → wipe → fade`。

### 1.3 命名

> 「我觉得这个更像是「**板书**」这样概念的 mode」 → 定名 `bansho`（日语「板書」）。

### 1.4 核心目标（反复强调，是验收的总纲）

> 「这个东西的核心，是绘制图表的动画，能根据内容，为了 presentation 的流畅性，
> 知识和概念传递的准确性和**娓娓道来循序渐进**的效果，**让 agent 很方便很舒服地设计板书的动画**。
> 甚至**内容和动画可以一气呵成**」

> 「bansho skill 可以让 agent **一读就知道，这是帮我传递我想表达的东西的**。。
> **而不是一个设计负担**，我有一堆工具要使用」

> 「**这个整体概念一定要到位～**」

**判据：agent 读完 skill 的感受是「有人在帮我表达」，不是「我要学一套工具」。**

### 1.5 方言形态

> 「你可以用一个融合语法～基础语法用类似 markdown 的形式，**尽可能利用大模型自己已有的
> 知识体系**。可以在需要的地方扩展语法。但是**整个内容读下来，就是有一种可以脑内渲染、
> 边写边说的板书效果的样子**～」

**「读下来能在脑内渲染」是方言设计的验收标准**，不是「语法完备」。

## 二、空间模型：黑板不是画布，是有限的物理表面

### 2.1 黑板面积配置

> 「既然是黑板，还需要支持一个指定黑板面积的模式…支持超大画布版本（类似无限画布，
> 但是有个**硬上限，系统防御性的**，至少保证前端渲染不太卡），然后用户可以指定一个面积
> （就像一个真的黑板，然后支持 4 种形式的黑板：**单块、2 块、3 块、4 块**，
> 跟各种大学校园的可移动黑板一样哈哈，**大家看过 MIT 的公开课都会超级亲切**）。
> 然后你一开始的模式就等于**单个长条的黑板尺寸配置**」

### 2.2 设计内核（这句是整个空间层的地基）

> 「**可以画的东西是物理受限的，可以移动的是画板的相对位置和镜头。
> 通过这些共同构成了「读者注意力与内容产生过程」的融合**」

形式化三条：墨迹是物质（画上去就长在那儿）· 舞台是可调度的（只有板位和镜头能动）·
二者同轴（注意力引导 = 内容产生过程本身，不是事后叠加的特效）。

### 2.3 擦除是表达（推翻了「刻意不擦」）

> 「**擦也是一种语义，一种表达**」
> 「我展开一个细节、跟你说清楚了，就可以擦掉，**因为黑板面积有限**」
> 「**能擦能擦。。为啥不能擦。。能擦能划掉，都是串行的。。黑板为啥不能擦。**」

**语义分工（必须守住）：** `~~划掉~~` = 我**否定**它，但你得继续看见；
`@erase` = 它**完成使命**了，腾地方。用错就是教错。

### 2.4 板 ≠ 笔记

> 「最后可以有一个**大而全**的网页版，变成一份「**课堂笔记**」，这不冲突不矛盾～」

同一份 canonical timeline 两种投影：板会擦、笔记什么都不丢。

## 三、画布转向：从「四页教科书」到有位置的内容

### 3.1 否决（2026-08-11，看完成品后）

> 「你现在内容的写法，就是假设黑板只能从上往下写。。**跟在读教科书没有任何区别**。」

> 「如果我是老师，我会把图画到**右边的空白位置**（**选择性的**），而不是一定往中间插入。。
> 后面一页的图表，又画了个巨大不合理的图，**明显信息不用占那么大的空间**。」

### 3.2 老师真实的书写流程（五步，是 `frame-board` 的需求本体）

> 1. 我先构思写什么（**可能不止一个**，比如 2 段话 + 1 个图 + 一个大标题标重点）
>    （**也有可能是对历史内容的补充、强化、修改**）
> 2. 我先**看一眼**现在的黑板已有的内容
> 3. **想象一个占位区域**，我写完这个内容之后，结果会变成什么样子
>    （如果明显空间已经不合理了，考虑擦除一些内容）
> 4. 真实去写上内容
> 5. 尝试**对比预期和实际的差距**，大致重叠就完成
>    （如果超出了范围，或导致大的变化例如换行到下个 board，**就重写**——
>    **这个重写不用体现在流程中，这属于播放动画的设计阶段，并非直播**）

**第 5 步括号里那句解开了一个死结**：我曾以「诚实的试算不可能便宜」为由永久拒绝落点预测；
按这个流程根本不需要预测——**写下去、看结果、不对就重写**，而重写免费是因为**创作不是直播**。

### 3.3 预览必须是贴图，不是渲染

> 「我这里说的所有的意图，都是用 tool call 调用由 viewer 提供的 api，得到一个
> 「**脑内渲染的占位图/示意图**」，用**半透明色块**去填充 + 截图，让 AI 来看。」
>
> 「这个前提是你的整个布局，**不能再是这样的 html 流自然布局**，
> 而是要用**画布 + 贴内容块**的形式来做了。」

**这句点破的是前提关系**：不是先想要 API 才改布局——**流式布局里「这块会落在哪」
没有独立答案**（位置是之前所有内容的后果）；画布上位置是**声明**的，
预览才可能既便宜又诚实。

### 3.4 三条拍板

> 「人也是**大致分区**，可以用**软**的方式，但是**渲染回来看的时候可以调整**」
> → 区域语义（不是像素坐标）；尺寸硬、后果软；调整发生在看过之后。

> 「写满怎么擦。。**应该是 Agent 自己**。。（而且如果他视而不见，下一步预测书写 intent 的时候，
> **应该会重叠**），然后**被 viewer 的自检 api 警告**，他看到警告会知道自己调整。」
> → **删掉自动擦除**。房间永不悄悄拆板；满了就是重叠，重叠看得见、被警告、agent 自己决定。

> 「**长卷也画布化**。。长卷也可以**有点斜** / **分成几个短文本框来引入不规则感**嘛」
> → 没有两种板；而且**即使只有一块板，把内容切成有位置的块本身就是反教科书的**。

### 3.5 命名

> 「1. 听你的 语意连贯清晰即可」→ `@at`
> 「2. 这个。。还是**别太抽象**。。`frame-board` 吧」→ 预览动作定名

## 四、三维与过渡感

### 4.1 脑洞与自我收敛（同一轮）

> 「按照现在的架构，是不是连黑板都可以做真正的 3d 变换。。就是直接在 three.js 里面
> 用真实的镜头 + 空间来上课！」
>
> 「我觉得是**注意力引导 + 空间变化产生的过渡感**。。所以确实 **css3d 应该就够了**」

**第二句就是需求本身**：要的是**过渡感**，不是三维物体。判据一给出，技术选型自动确定。

### 4.2 分层

> 「css3d 提供的是**可以 3d 变换的黑板**，应该不影响的」
> → 交付**能力**，不交付**玩法**；哪些教学动作消费它是后续的事。

**配套边界（我提、被采纳）：纵深只在过渡里出现，稳态永远正对**——
被讲的板必须正面朝读者、字不斜，因为那一刻它的工作是**被读**。

### 4.3 视差开关

> 「你可以在 viewer 上给个小开关，允许**鼠标模拟轻度的摇晃**，获得一个小幅度的晃动感～
> 哈哈哈 **这样就可以让用户直接感知到了**」

**它同时是探针**：真三维会跑出视差，假透视一晃就穿帮——**验证的人和体验的人看到的是同一件事**。

## 五、「感觉」清单 —— 这一节是本文的重点

产品负责人给的需求里，**关于「感觉」的比关于「功能」的更多，也更容易在技术讨论中被盖掉**。
逐条列出，每条都是独立的验收项。

### 5.1 缓动：不能全线性

> 「对于镜头的缩放啥的，都需要 **ease** 让整个动画保住理解。。**最好不要全是线性的。。会很难受**哈哈」

落法：Van Wijk & Nuij 平滑缩放-平移（同时平移+缩放时线性插值在**感知上是错的**——
画面会先冲出去再拉回来）；每种笔有各自的速度性格且**严格单调**（不单调会让回拖时画面倒着走）。
**状态：已落地。**

### 5.2 手写：公式不能是印刷体

> 「我希望**能用手写感觉的东西都用手写感觉**，尤其是公式的部分，我看你之前公式的效果，
> **太工整了。。完全没有手写板书的感觉**」

根因（查实）：浏览器 UA 样式表强制 MathML 用数学字体，外加 `text-transform: math-auto`
把变量重映射到手写字体不覆盖的 Unicode 区段——**光换字体会静默 fallback**。
落法：字体继承 + 关掉那个变换 + 每字形定种子微抖 + **分数线是画出来的**。
**状态：已落地（自评约 85%；根号与可伸缩括号仍是印刷体，理由是尺寸变体表手写字体没有）。**

### 5.3 瑕疵：书写仿真

> 「影响真实感的，是**瑕疵**。我觉得需要尝试添加扰动，例如**意料之外的错别字（涂掉再写旁边）**，
> 例如**粉笔随机周边的点击，没有那么干净的黑板**。**书写区域的四边形随机旋转和形变
> （我们写字有时也会斜）**。这些程度都**可以配置，调成 0 就是干干净净**的状态。
> 但是真实场景可能需要有变化一点。**这个跟你划线模拟的那种不直的效果是一类的，
> 都是在做书写仿真**」

我提的切分（未被否，也未细谈）：
- **只花像素的**（粉笔屑、板面不洁、**擦过留残影**、整板轻微歪斜、行基线漂移）→
  一个强度旋钮，0 = 干净。不占时间、不进 canonical。
- **要花时间的**（错别字、涂掉、旁边重写）→ 占时间轴、改变读者读到的字、
  回拖必须每次一样。**我的判断：错别字应是作者用的动词，不是引擎随机撒的**——
  随机撒可能正好涂掉要讲的那个词，那是教学伤害。**待产品负责人选。**

**两条硬约束**：墨迹必须跟着变形走（整板歪斜免费、每行漂移可行、**每行独立旋转**
会让轴对齐的墨迹层跟不上）；**扰动必须定种子**（同一份讲稿永远同一份瑕疵）。

**状态：❌ 完全未做。** 这是「极致手写感」里最后一块没动的，也是本文档里
**分量最重的未兑现项**。

### 5.4 换板必须看得见

> 「**切换白板没有任何动画，完全看不出来换了**」

**「看不见移动，四块板就等于四页 PPT」。** 根因是舞台调度被门在了「板上写了镜头指令」
之后，而只用 `@turn` 的讲稿根本不建调度。
**状态：已修，13/13 次换板都有走位**（含橡皮走去擦板、书写迁移、图表层）。

### 5.5 板要写满了才换

> 「**内容没用满就换，毫无意义的布局**，而且只有从上往下，依旧没有任何有效空间利用」

实测四块板只用了 76%/74%/74%/64%，最后一块**只有 1 步**。
根因是 skill 教错了动机（「新话题就换板」），**真老师换板是因为没地方了**。
**状态：教学已改；「工具该不该主动说这次换早了」的 finding 推荐但未建。**

### 5.6 要有鸟瞰

> 「**没有总览/鸟瞰的界面，不知道有多少板**」

早期还提过缩略图：
> 「右下角的缩略图**需要模拟真实的情况**吧。。只是 3 个框，有点信息不够啊」

**状态：已做**——四个格子（有几块板）+ 高亮（在哪块）+ 填充条（写了多满）+ 点击跳转。

### 5.7 板要能上手

> 「整个 board 我也无法操作呀～至少拖拽的时候可以让我**像无限画布一样去操作**。。
> **你可以拖拽时暂停部分。。继续的时候回到之前的位置**～」

第二句是设计不是抱怨：**抓住暂停、松手不恢复、按播放才回到笔尖**。
（我曾以「与点选、文本选中冲突」为由拒绝拖拽，被推翻——**冲突是真的，结论是懒的**。）
**状态：已落地**（阈值鼠标 4px / 手指 10px；`alt+拖拽` 保留文本选择；触屏单指平移一并补上）。

### 5.8 总纲

> 「我不知道你是怎么理解白板的。。**如果视觉不看，那这个模式毫无意义。**」

**这是最重的一句。** 这个 mode 卖的就是「看见思考发生的过程」——
测试全绿而东西不像黑板，等于零。

## 六、agent 的眼睛

### 6.1 鸟瞰是给 AI 的，不只是给人的

> 「你需要有个当前的类似 outline 或者鸟瞰，**来引导 AI 写内容**，
> 不然写着写着，**他对自己已经在板书上写了什么就没概念了**」

### 6.2 抬头看一眼的节奏

> 「引导他每次更变内容，都利用这个 viewer 的 api，看一下 outline 图或者现状的快照，
> 再决定怎么新增/修改/擦除。**就像一个真的老师一样。讲到下一部分的时候，
> 是找空白黑板，还是擦掉不要说的部分，都需要抬头看一眼。**」

**这是节奏，不是参考资料**：`看 → 决定 → 落笔`。而且**正因为板面有限才必须抬头**——
工具应当复现这个约束，而不是绕开。

**推论**：必须便宜到能每步都调（贵了就没人调，循环当场死）。

### 6.3 viewer API 是眼睛

> 「这些应该进 skill，教会 agent 如何利用好 viewer 的 API 来帮助他，
> **这就是他的眼睛和工具**。**所有内容的效果，他不能光靠想象**。」

与 `.claude/rules/frontend.md` 对我的约束是同一条原则，往下落了一层。
**状态：`glance-board`（看）· `check-board`（诊）· `capture`/`frame-board`（验）三器官已建；
但盲测显示教学仍有缺口——见 §8.2。**

## 八、工作方式（这些也是需求）

### 8.1 分工

> 「你的编程任务就让 **opus** 来做吧～复杂问题引入 **fable 做 advisor** 就好了」

> 「反正你弄完总是让 **codex 端到端看一看，多用视觉能力去做 e2e**。。**你别自己做～**」

理由（实证）：舞台层我自己跑遍门禁判定合格，Codex 一进来找出 6 条、4 条 P1——
其中两条是「**测试与实现互相同意，两者一起违背契约**」，门禁结构上抓不到，
**因为门禁本身就是同意的一方**。

### 8.2 零泄题盲测（最重要的一条方法论）

> 「你的核心还是要让 **codex 在 0 leak 的情况下，根据你的 skill 自己做自己看，
> 自己发现问题**。。这样来**证明设计已经没有问题了**」

做法：全新空工作区、只有装出去的 skill、零示例、任务书不提任何内部概念。

**首次结果（2026-08-11）：它做成了**（4:48、91 步、四块板，自己发现并修了三处问题），
**但它一个 `@at` 都没用**——`@turn` ×10、`@erase` ×8、`@at` ×0。
它**遇到了 `@at` 要解决的问题**（图表吃满整面墙），**用擦除绕过去了**。

**这条是本文档里最重要的未决问题**：语法文档现在有了，
但**没有任何时刻告诉 agent「此刻该考虑摆位置」**。
一次盲测不足以动方言，**需要第二次盲测判定**。

### 8.3 节奏

> 「不用等我把后续 v2 都做完，然后自己做个 e2e 测试」
> 「我想你整体实现了之后再一起调整，不然等会又要重新改」

## 十、汇编时发现的一件事

把两天的原话排在一起之后有一个模式很明显：

**关于「感觉」的需求（§5）有 8 条，关于「功能」的需求少得多；
而工程投入的分布恰好相反。** 缓动、手写公式、瑕疵、走位、鸟瞰、拖拽手感、
「视觉不看就毫无意义」——这些每一条都被单独提出来过，其中**瑕疵那条至今零投入**。

而三次否决（「跟读教科书没区别」「你好像一直在用第一版的概念」「视觉不看毫无意义」）
**全部来自看效果，没有一次来自看代码或看测试**。

这条写在这里，是给未来的自己看的：**这个产品的验收发生在眼睛里。**
