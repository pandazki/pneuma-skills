# Bansho —「抬头看一眼」：板面快照 设计意图书

> 产品负责人 2026-08-10 提出。这份文件只记**意图与约束**，不定方案——
> 方案交给 architect。写在这里是因为原话里的框架比我自己的准，不能被转述磨掉。

---

## 原话

> 「我觉得你需要有个当前的类似 outline 或者鸟瞰，来引导 AI 写内容，
> 不然写着写着，他对自己已经在板书上写了什么就没概念了。」
>
> 「做的过程中，可能需要引导他每次更变内容，都利用这个 viewer 的 API，
> 看一下 outline 图或者现状的快照，再决定怎么新增/修改/擦除。**就像一个真的老师一样。
> 讲到下一部分的时候，是找空白黑板，还是擦掉不要说的部分，都需要抬头看一眼。**」

## 框架：这不是一份参考资料，是写作循环里的一个动作

我最初的理解是「给 agent 一张地图」——错在把它当成可选的参考。
产品负责人说的是**节奏**：

```
抬头看 → 决定（找空板 / 擦掉讲完的 / 接着写）→ 落笔
```

这是老师在真实黑板前每隔一段就会做的事，而且**正是因为板面有限才必须做**。
这个 mode 的设计内核是「可以画的东西是物理受限的」——
物理受限逼出抬头，工具应当复现这个约束，而不是绕过它。

**推论（对方案的硬要求）：**

- **必须便宜到能每次落笔前都调。** 贵了 agent 就不调，循环就不成立。
  压缩是一等需求，不是优化项。
- **必须回答"决定"所需的信息，而不是罗列全部事实。** 见下面三个问题。
- **技能文档要教这个节奏**，不能只写"困惑时可以调用"。

## 抬头时，老师实际在问什么（方案要能回答这三个）

1. **还有空地方吗？** —— 当前板还剩多少、有没有整块空板。
   这是「找空白黑板 vs 擦掉」这个决策的**唯一输入**。
2. **哪块可以擦了？** —— 每块板上现在站着什么、属于哪一段、是不是已经讲完。
   擦除是表达（「它完成使命了」），所以要能看出"完成了没有"。
3. **我刚才写的还在不在？** —— 哪些文字仍然站在板上、因而仍然可以被
   `@focus` / `@erase` / `@circle` 锚定。
   这条在本轮 P1-1 修复后变成硬需求：**指向已擦内容现在会响亮报错**，
   所以作者必须能在落笔前看出某个锚点是否还有效。

## 已经确定的原则

- **派生，绝不手写。** 快照必须从 `board.md` + 折叠算出来。
  让 agent 自己维护一份大纲文件，一定会漂移，而**漂移的地图比没有地图更糟**。
  这与本 mode 拒绝让 agent 手写时间戳是同一条纪律。
- **它是同一份 canonical timeline 的第三个投影。**
  板（播放态）· 笔记（导出态）· **快照（状态态）**。
  不是新机制，是既有解耦的自然延伸——这也意味着它同时该有**人看的视图**
  和**agent 调的动作**，一次计算两个消费者。
- **零新增磁盘状态面。** 纯投影，不落盘。

## 交给 architect 的开放问题（不 gate 方向，但要答）

1. **"现在"是什么时刻？** agent 在时间轴末尾追加，所以它要的是 t=末尾的板面；
   而人在播放时看到的是 playhead 处的板面。两个消费者的"现在"不同——
   是同一投影的不同入参，还是两件事？
2. **抬头需要板面先追上。** 板归属依赖实测高度，测量发生在 viewer。
   agent 刚追加完就抬头，viewer 可能还没测完——动作是等测量完成再答，
   还是可以答一个"尚未测量"的诚实状态？这决定了循环是否可靠。
3. **压缩到什么粒度还能支撑决策？** 每步一行在 200 步的板上就是 200 行。
   站着的长段落该折叠成「§1 …7 步，站在第 1 块板」吗？
   折叠到什么程度就答不了上面那三个问题了？
4. **修改（不只是新增）时抬头看什么？** 原话点了"新增/修改/擦除"三种。
   改中段会引起下游板归属平移（R4 族），快照要不要能预示这件事？

## 与已有面的关系

- `check-board` 回答的是「**有没有错**」；快照回答的是「**现在是什么样**」。
  两者互补，不要合并——一个是诊断，一个是感知。
- 笔记视图已经证明「同一份 timeline 两种呈现」在这个 mode 里成本极低；
  第三种投影应当同样便宜。
