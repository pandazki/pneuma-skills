写给做决策的人

大语言模型到底在做什么，以及它会在哪儿咬你一口

读者产品经理 阅读约 4 分钟 用途立项判断、方案评审

它是一个「猜下一个字」的机器。把海量文本喂给它，让它反复练习「给定前面的内容，下一个字最可能是什么」，练到足够好，就能一个字一个字地把一整段话生成出来。

这句话不是打比方，是它真实的工作方式。你在产品上遇到的所有惊喜和所有麻烦，几乎都能从这一句推出来。

按字数计费
输入和输出都算钱。对话越长，每多说一轮就越贵。
同问不同答
它是从概率里采样的，同一个问题问两次，答案未必一样。
知识有截止
训练数据停在某个时间点，之后的事它一概不知。

为什么「猜字」能变成「像是懂了」

要把下一个字猜准，它被迫学会了很多东西：语法、常见事实、代码怎么写、一段论证怎么往下走。这些不是有人教给它的条目，而是「猜得准」这个目标顺带逼出来的能力。

所以它的表现有个特点——能力和可靠性是两件事。它能写出一段结构漂亮、术语准确、读起来很专业的文字，同时里面某个关键数字是编的。这两件事在它身上不矛盾，因为它优化的目标从来不是「说真话」，而是「像训练时见过的那种话」。

能力边界

它做得好的

  • 改写、润色、翻译、换一种语气重说一遍
  • 从一段长文里抽出结构化信息
  • 分类、打标、按规则判断
  • 写初稿：文案、邮件、代码骨架
  • 把你给它的材料读懂，然后基于材料回答

它做不好的

  • 精确算术和多步计算（要外接工具）
  • 需要「查得准」的事实问答（要外接检索）
  • 要求每次输出完全一致的场景
  • 它没见过的私有数据——不喂给它就是不知道
  • 需要为结果负法律或安全责任的最终判定

右边这一列不是「以后会好」的清单，其中几项是机制决定的。正确的做法是在产品设计里绕开，而不是等模型变强：算术交给计算器，事实交给检索，一致性交给模板和缓存。

成本长什么样

计价单位是 token，可以粗略理解成「字」——中文一个字大致就是一到两个 token，英文一个常见单词约一个。要记住三件事：

  • 输入也收费。你塞给它的提示词、检索到的资料、历史对话，全都按量计费。很多项目的成本大头在输入而不是输出。
  • 多轮对话是累加的。模型本身不记得上一轮，是你每次把整段历史重新发过去。第十轮的单次成本可能是第一轮的好几倍——这条最容易在上线后才被发现。
  • 贵的模型不总是划算，便宜的也不总是省钱。小模型答不好会触发重试、人工介入或用户流失，这些成本不出现在 API 账单上。要按「一次成功交付的总成本」比，不要按单价比。

三类风险，以及怎么兜

风险它为什么会发生产品上怎么兜
一本正经地编 它在补一个「读起来最顺」的答案。没有材料支撑时，它不会空着，会补一个像样的。 把材料喂进去再让它答；输出附出处；关键字段做校验；界面上让人一眼看出哪些是模型说的。
结果不稳定 生成过程带随机采样，同样的输入可能走到不同的路径上。 要结构化就约定输出格式并做解析校验；能缓存的缓存；上线前用固定的评测集跑回归，别靠手动试几条。
说了不该说的 它的目标是把话接下去，不天然理解你的合规边界和业务口径。 系统提示写清楚边界；输出侧加审核；高风险动作一律留人工确认这一步。

顺带一提：它不会「越用越懂你」

模型参数在你调用的时候是冻结的。它显得记得你，是因为有人把历史又发了一遍给它。所谓「个性化」，在工程上其实是「你存了什么、又塞了多少回去」——这是一个存储和检索问题，不是模型问题。想清楚这一点，很多需求的实现路径会立刻变得具体。

立项前值得问的五个问题

  1. 这个功能答错一次，代价是什么？ 代价是「用户重写一遍」还是「赔钱」，决定了兜底要做到多重。
  2. 答案能从我们自己的数据里找到吗？ 能，就该做检索加生成；不能，就要接受它在凭印象说话。
  3. 怎么判断这次输出是好的？ 说不出验收标准，就没法回归、没法迭代，也没法判断换模型是变好了还是变差了。
  4. 单次调用要塞进去多少内容，上限在哪？ 这一条直接决定单位成本和响应时间，而且会随使用时长悄悄上涨。
  5. 出错的时候，用户能自己救回来吗？ 一个好用的「重来 / 编辑 / 转人工」，往往比再调半天提示词有用。
不要得出的结论：「它现在还不准，等下一代模型就行了。」有些问题会随模型变强而缓解，但「它可能自信地说错」是这套机制自带的属性，不是这一代的缺陷。把产品建在「它偶尔会错、而我们接得住」的假设上，比建在「它以后不会错」上要稳得多。
想看它内部到底怎么算的——token、注意力、训练和推理的区别——梯子上还有「工程师」那一级。
