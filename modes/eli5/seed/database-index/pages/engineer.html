What a database index actually is

An auxiliary, ordered data structure the storage engine maintains alongside a table, mapping key values to row locations — so a predicate can be answered by traversal instead of by scanning.

01The structure

Unless you asked for something else, your index is a B+tree. Postgres implements a Lehman–Yao B-link variant; InnoDB, SQL Server and Oracle all ship close cousins. Two properties matter:

  • All keys live in the leaves. Internal nodes hold only separator keys and child pointers, so their fanout is high and the tree is shallow.
  • Leaves are linked to their siblings. Once you have found the first matching key, a range scan walks sideways through leaf pages — no re-descending the tree per row.

02What a lookup costs

Access pathComplexityWhat you actually pay
Sequential scan O(N) Sequential I/O and cheap per page — which is why it wins when a predicate matches a large slice of the table.
B+tree point lookup O(log N) Height-many page accesses, ~3–4, of which usually only the leaf misses cache.
B+tree range, k rows O(log N + k) One descent, then sideways along the leaf chain.
Hash index, equality O(1) expected Equality only. No ordering, no ranges, no prefix matching.

The asymptotics hide the interesting part: an index scan does random I/O, a sequential scan does sequential I/O. That constant factor is why the planner will refuse your index when the predicate matches a large fraction of the table.

03In practice

-- 8.4M rows, no index on customer_id
EXPLAIN ANALYZE SELECT id, total_cents, placed_at
FROM orders WHERE customer_id = 90210;

Seq Scan on orders  (rows=41 loops=1)
  Filter: (customer_id = 90210)
  Rows Removed by Filter: 8419612
  Execution Time: 2417.883 ms

-- build it without blocking writes on a live table
CREATE INDEX CONCURRENTLY idx_orders_customer_id
  ON orders (customer_id);

-- same query, same data
Index Scan using idx_orders_customer_id on orders  (rows=41 loops=1)
  Index Cond: (customer_id = 90210)
  Execution Time: 3.914 ms

Two things to note. CONCURRENTLY builds the index without taking a write lock — it costs a second table pass and can leave an invalid index if it fails, but it is what you use on anything in production. And Rows Removed by Filter is the number to look for in a plan: eight million rows read to return forty-one is the definition of a missing index.

04Composite indexes and the leftmost prefix

CREATE INDEX idx_orders_cust_status_date
  ON orders (customer_id, status, placed_at DESC);

The index is sorted by the tuple (customer_id, status, placed_at), in that order. That means it serves:

  • WHERE customer_id = ? — leading column alone.
  • WHERE customer_id = ? AND status = ? — leading pair.
  • WHERE customer_id = ? AND status = ? ORDER BY placed_at DESC — equality on the prefix, then the third column is already in the requested order, so the sort disappears from the plan.

It does not usefully serve WHERE status = ? alone. Nothing constrains the leading column, so there is no contiguous range to descend to. Order your columns by the shape of the predicate: equality columns first, the range or sort column last.

One range ends the useful prefix. In (a, b, c), once you use an inequality on b, the entries matching it are spread across many b values, so c is no longer sorted within the scanned range. Postgres can still apply c as a filter on the entries it visits, but it cannot use it to narrow the scan or skip a sort.

05Covering indexes, and the fetch you forgot about

Finding the index entry is not the same as having the row. What happens next is engine-specific, and it is the most commonly skipped step in a mental model:

EngineLeaf entry holdsCost to get the row
PostgreSQL A TID — physical (page, offset) into the heap One extra random heap read, unless the query is index-only and the visibility map marks the page all-visible.
InnoDB (MySQL) The primary key value A second descent, this time through the clustered index, unless the secondary index already covers every column the query needs.

You avoid the fetch by making the index cover the query — putting every referenced column in it:

-- payload columns ride along in the leaves, not in the sort key
CREATE INDEX idx_orders_cust_covering
  ON orders (customer_id) INCLUDE (total_cents, placed_at);

-- plan becomes:
Index Only Scan using idx_orders_cust_covering on orders
  Heap Fetches: 0

INCLUDE (Postgres 11+) is the honest way to do this: the extra columns are stored in leaf pages only, so they widen the leaves without widening the internal nodes or affecting the key ordering. Cramming payload into the key tuple instead makes the tree taller and the sort semantics wrong.

Heap Fetches: 0 is what you are actually checking for. In Postgres an index-only scan still consults the visibility map, and on a table with heavy recent churn it will fall back to heap reads until autovacuum catches up.

06Why the planner ignored your index

  • The predicate is not selective enough. If statistics say it matches ~20%+ of rows, random-access-per-row loses to a sequential scan. The planner is right; add a more selective column or accept the scan.
  • The column is wrapped in a function. WHERE lower(email) = ? cannot use an index on email. Build the expression index — CREATE INDEX ON users (lower(email)) — or normalise on write.
  • An implicit cast lands on the column side. A predicate that has to convert every stored value before comparing is not sargable. Cast the literal, not the column.
  • Leading wildcard. LIKE 'acme%' is a prefix range and a B-tree can serve it; LIKE '%acme' is not, and needs a trigram or full-text index. In Postgres, prefix matching on a non-C collation additionally requires text_pattern_ops.
  • Stale statistics. After a bulk load the planner is costing a table it thinks is tiny. ANALYZE before you conclude anything about a plan.
  • NULL semantics. IS NULL is indexable in Postgres, but a partial index built WHERE col IS NOT NULL obviously cannot answer it.

07What every index costs on the write path

Each insert, delete, and qualifying update maintains every index on the table. Three specifics worth carrying around:

  • Random keys split pages. A monotonic key appends to the rightmost leaf. A random one (UUIDv4 as a primary key is the classic) inserts into arbitrary leaves, forcing splits and leaving pages half-full. UUIDv7 or ULID restores time-ordering and most of the locality.
  • Postgres HOT updates skip index maintenance when no indexed column changed and the new tuple fits on the same heap page. Every extra index widens the set of columns that can break that condition — an index on a frequently-updated column silently disables HOT for the whole row.
  • Unused indexes never stop charging. They cost write time, storage, and vacuum work forever. pg_stat_user_indexes.idx_scan tells you which ones have never been read since the last stats reset.

08When a B-tree is the wrong tool

TypeReach for it whenCost
btree Equality, ranges, sorting, prefix matching. The default, and correct ~90% of the time. Baseline.
hash Equality only, on a wide key where the B-tree entry would be large. No ranges, no ordering. Rarely worth the specialisation.
gin One row contains many searchable values — jsonb, arrays, full-text vectors, trigrams. Slow to update; batch inserts benefit from a pending-list configuration.
gist Geometry, ranges, nearest-neighbour ordering, exclusion constraints. Lossy for some types — results may need rechecking against the heap.
brin Very large tables whose physical order correlates with the column — append-only time series is the canonical case. Tiny (kilobytes for gigabytes of table), but useless the moment that correlation breaks.

And the partial index, which is underused

-- 0.3% of rows are pending; index only those
CREATE INDEX idx_orders_pending ON orders (placed_at)
  WHERE status = 'pending';

A predicate the planner can prove implies the index's WHERE clause gets an index a fraction of the full size, with a correspondingly smaller write cost — and rows outside the predicate are not maintained at all. When a hot query always carries the same narrow filter, this beats a composite index on both columns.
