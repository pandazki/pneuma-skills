Plain-language brief

What a database index is, and what it costs

Audience Engineering manager Read time 3 minutes Decision Yes — see the last section

An index is a lookup shortcut the database keeps beside a table so it can jump straight to the rows you asked for instead of reading every row to find them.

Adding the right index is usually the single cheapest performance fix available: hours of work, no product change, and a slow screen becomes an instant one. It is not free — indexes take disk space and make writes slightly slower — but for most read-heavy tables that trade is strongly in your favour.

The one-line version

It is the index at the back of a reference book. Without it you read every page to find the one mention of a term. With it you check three lines and turn to page 412. The index costs a few pages and has to be rebuilt if the book changes — that is the entire trade.

What it costs you

DimensionWhat actually happens
Engineering time Hours, not weeks. Identifying the right column is the work; creating the index is one command. On a large live table it should be created without locking writes, which takes longer to run but needs no downtime.
Storage Typically 5–20% of the table's size per index. Real money at scale, rounding error below a few hundred GB.
Write speed Every insert, update, or delete has to maintain every index on the table. One or two indexes: negligible. Twelve indexes on a hot write path: measurable, and a common cause of mysterious write slowdowns.
Ongoing risk Low. Indexes are invisible to the application — the code does not change, and one can be dropped again in seconds if it turns out not to help.

When an index will not save you

This is the part that usually does not get said out loud, and it is where teams lose weeks:

  • The column barely narrows anything. Indexing a status column that is active for 90% of rows does not help — the database still has to visit almost every row, and it will sensibly ignore the index.
  • The table is small. Under a few thousand rows, reading everything is already fast. An index here is noise.
  • The table is written far more than it is read. Event and audit tables often fall here; every index is a tax on the write path with little read benefit.
  • The query is slow for a different reason. Missing pagination, an N+1 query loop, or fetching a million rows to display twenty. An index will not rescue any of those, and reaching for one first can hide the real problem for months.
  • Nobody removed the old ones. Indexes accumulate. Unused indexes cost storage and write speed forever and give nothing back.

What to ask when someone proposes one

  1. Which query is slow, and how slow is it today? Turns "the app feels sluggish" into something you can verify afterwards.
  2. What fraction of the table does the filter actually match? If the honest answer is "most of it", an index is the wrong fix.
  3. How many indexes does this table already carry, and are they all used? The write cost is cumulative, and databases can report which indexes are never touched.
One thing not to conclude: "so we should index everything." Indexes are a targeted instrument. Applied per slow query they are among the best returns in engineering; applied by default to every column they quietly make every write slower and every backup larger, and nobody notices until the write path is the outage.
